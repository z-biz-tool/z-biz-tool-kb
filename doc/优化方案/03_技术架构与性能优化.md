## 3.1 存储引擎与索引（首要技术决策）

**现状**：每文档两个 JSON 文件（`documents/{id}.json` 元数据 + `chunks/{id}.json` 切片数组），直接 `fs::write`（[../../src-tauri/src/rag.rs](../../src-tauri/src/rag.rs) L200-L232），列举 = 遍历目录逐个解析（L235-L259、L277-L299）。

**推荐：单文件 SQLite（WAL 模式）+ FTS5 全文索引**，通过 `rusqlate`（bundled 特性，静态链接 SQLite，避免系统库版本差异）。理由：

1. 一次性解决 D-05（无索引全量扫描）、D-15（零容错/非原子写）、D-16（并发写）三个缺陷：事务原子性、崩溃恢复、WAL 并发读是 SQLite 的既有保证，不需要自研；
2. FTS5 自带 BM25 排序与 `snippet()`/`highlight()`，直接支撑"检索可解释"（命中词高亮）与 02 文档的全局搜索；
3. 单文件便于备份/导出/迁移（02 文档 §2.9 整库导出即拷一个文件 + originals/）；
4. 桌面单机、单用户、万级条目规模，SQLite 远未到瓶颈；引入服务端数据库或嵌入式 KV（sled 等）都是过度设计。

**目录布局（规划新增）**：

```
app_data_dir/
├── knowledge.db          # SQLite：元数据 + 切片 + FTS + 会话 + 链接
├── knowledge.db-wal / -shm
├── originals/{doc_id}/…  # 上传原文留存（02 文档 §2.2-4）
└── backups/              # 自动备份（04 文档 §4.2）
```

`llm_config.json` 迁移：非密钥字段进 db `settings` 表，api_key 进 OS keychain（04 文档 §4.3）。

**JSON 旧数据迁移**：启动时检测 `documents/`、`chunks/` 目录存在且 db 无迁移标记 → 逐文件导入 SQLite（单事务），成功后将旧目录改名为 `documents.migrated/` 保留一个版本周期，回滚方案见 [05 文档 §5.6](./05_实施路线与任务拆解.md)。

**Rust 模块重构**：`rag.rs` 已 484 行承载五种职责，按关注点拆分（规划新增文件）：`src-tauri/src/storage/`（db 连接与 DAO）、`extraction.rs`（文本提取）、`chunking.rs`（切片）、`retrieval.rs`（检索管线）、`llm.rs`（API 调用）；`commands.rs` 只做参数校验与编排。

## 3.2 检索管线（明确推荐）

**现状**：查询侧中文 2-gram + 英文小写分词，文档侧无索引，打分 = 子串命中计数 / 字节长度因子（[../../src-tauri/src/rag.rs](../../src-tauri/src/rag.rs) L307-L358，D-06）。

**推荐管线（阶段三落地）**：

```
查询 → 规范化(小写/全半角/去噪) → 分词(与索引侧同一套) → FTS5 MATCH
     → BM25 排序 → [可选] 向量召回 → RRF 融合 → Top-N + snippet + 命中词解释
```

**中文分词方案（关键决策）**：FTS5 内置 `unicode61` 对 CJK 不分词（连续汉字成一个 token，基本不可用）；`trigram` tokenizer 可用但查询短于 3 字退化。**推荐：索引侧用 `jieba-rs` 预分词**——写入时把 `切分后空格连接的文本` 存入 FTS 列（原文存普通列），查询时对 query 做同样分词后拼 MATCH 表达式。分词器版本与自定义词典记入 db 元信息，升级分词器 = 触发全量重建索引（后台任务，见 §3.3）。

**是否引入向量检索（权衡后明确：阶段五再决策，默认先不引入）**：

| 维度 | 引入 | 不引入 |
| --- | --- | --- |
| 收益 | 换说法/同义改写可召回（"怎么退钱"↔"退款流程"） | — |
| 成本 | 需 embedding 服务（外部 API 泄露知识内容 / 本地 Ollama 增加安装门槛）、每切片一次调用、重建索引成本 | 零 |
| 隐私 | 文档内容出境到 embedding API，与"本地优先"卖点冲突 | 内容不出本机 |

决策规则（可测量、不拍脑袋）：阶段三先建评测集（§3.7）测 BM25 基线；**当且仅当**评测集中"改写类查询"（同义换词，占评测集 ≥ 20%）的 Recall@5 比字面匹配类低 15 个百分点以上，才启动向量路线。若启动，推荐形态：embedding 走用户已配置的 OpenAI 兼容网关（复用 LlmConfig，新增 embedding model 字段）或本地 Ollama；向量存 SQLite blob；**万级切片内直接暴力扫描余弦相似**（5k × 768 维 f32 ≈ 15MB，单次全量计算 < 50ms，无需 HNSW/专用向量库——明确不引入 Qdrant 类外部服务）。融合用 RRF（倒数排名融合），保持两路分数不必可比。

**LLM 上下文预算（现状缺陷）**：Top-5 切片全文拼接无 token 上限（[../../src-tauri/src/commands.rs](../../src-tauri/src/commands.rs) L159-L164），切片变大或 top_n 调大后可能超模型上下文。推荐：按估算 token 预算（默认 6000，可配）贪心装入，超预算截断并在 UI 标注"另有 N 条命中未纳入上下文"。

**流式输出**：`call_llm` 改 `stream: true` + SSE 逐段解析（reqwest 已支持 bytes_stream），经 Tauri event 推给前端（替换假打字机，D-13）；错误处理保留现有降级策略（C-02）。

## 3.3 增量索引与入库管线

**现状**：上传是同步单命令内"读全文→切片→写两 JSON"（commands.rs L20-L74），无中间状态（status 恒为 "ready"，L60），失败即无痕。

**推荐：状态机 + 后台任务队列**：

```
documents.status: pending → extracting → chunking → indexing → ready
                                                    ↘ failed(error_msg)
```

- 上传命令只做：校验（大小/类型/去重，04 文档 §4.1）→ 复制原文到 `originals/` → 插入 pending 行 → 立即返回 doc_id；
- 后台 worker（tokio spawn_blocking 池，并发度 2）按状态推进，每步一个事务；失败停在 `failed` 并记录可读错误，UI 可重试；
- 进度经 `import-progress` 事件推送（02 文档 §2.7）；
- **增量重建**：修改切片参数或分词器版本时，仅重跑 `chunking→indexing`（原文已留存，无需用户重新上传）——这是"原文留存"在架构上的第二重收益；
- 前端 `DocumentList` 的 status 渲染逻辑已支持 processing/failed（[../../src/components/DocumentList.tsx](../../src/components/DocumentList.tsx) L54-L73），后端补齐真实状态即可点亮。

**文本提取修复（D-01/D-02，阶段一）**：PDF 用 `pdf-extract` crate（或 `lopdf` + 自研文本层提取，若 pdf-extract 对中文 CID 字体表现不佳则换 `pdftotext` 二进制依赖——决策点在阶段一 spike，验收口径见 06 文档 UNIT-02 用例）；docx 用 `zip` + `quick-xml` 解析 `word/document.xml`；`.doc` 老格式明确降级为"不支持，给出可读错误并建议转 docx"（引入 antiword 类依赖收益低）。提取产物附带 locator（页码/段落，支撑 02 文档 §2.5 引用定位）。

**切片策略升级（D-17）**：结构感知切片——按标题层级/段落边界聚合到目标大小（默认 500 字，可配 200–2000），overlap 保留但强制 `overlap < chunk_size` 校验（修死循环隐患）；Markdown 保留标题路径写入 `chunk.heading_path`，检索时标题命中加权。参数存 db `settings` 表，不再硬编码。

## 3.4 大规模条目性能设计

现状在百篇内可用，以下为 1k–10k 文档规模的预防性设计（拟定量级估算，验收以 06 文档 PERF 用例实测为准）：

| 关注点 | 设计 |
| --- | --- |
| 列表 | 文档列表分页（每页 50）+ 排序索引 `(created_at DESC)`；不做全量返回 |
| 检索 | FTS5 倒排索引，复杂度与命中数相关而非库大小；BM25 由 SQLite 计算 |
| 切片文本 | FTS 表 `content=''`（external content 或 contentless）+ 正文存主表，检索命中后按 rowid 回表取文，避免索引双份存储 |
| 问答 IO | 只取 Top-N 切片正文，杜绝 `load_all_chunks` 模式（D-05 根除） |
| 向量（若引入） | blob 全表扫描上限 5 万切片；超过则评估 sqlite-vec 扩展，不提前引入 |
| 内存 | 提取大文件时用流式读取（BufReader 按段处理），单文件内存峰值目标 < 3× 文件大小 |
| 启动 | 冷启动只做 db 打开 + 迁移检查，不预载任何切片 |

## 3.5 数据模型与 schema 演进

**推荐 v1 schema（SQLite DDL 摘要，规划新增）**：

```sql
PRAGMA user_version = 1;                -- schema 版本，迁移依据

CREATE TABLE documents (
  id TEXT PRIMARY KEY,                  -- uuid v4，不再用"文件名_时间戳"
  title TEXT NOT NULL,
  source_type TEXT NOT NULL,            -- upload | note | clipboard | ai_draft
  source_uri TEXT,                      -- 原文件绝对路径 / URL / NULL
  original_path TEXT,                   -- originals/ 内相对路径，NULL=未留存
  content_hash TEXT UNIQUE,             -- SHA-256，去重（04 文档 §4.1）
  doc_type TEXT, size_bytes INTEGER,
  status TEXT NOT NULL,                 -- pending…ready/failed/trashed
  error_msg TEXT,
  extractor_ver TEXT, chunker_ver TEXT, tokenizer_ver TEXT,
  created_at TEXT, updated_at TEXT, deleted_at TEXT   -- deleted_at=软删除（回收站）
);

CREATE TABLE chunks (
  id INTEGER PRIMARY KEY,
  doc_id TEXT NOT NULL REFERENCES documents(id) ON DELETE CASCADE,
  idx INTEGER NOT NULL,                 -- 文档内序号
  heading_path TEXT, locator TEXT,      -- "§2 > §2.3" / "p12" / "L100-L142"
  text TEXT NOT NULL,
  tokenized_text TEXT NOT NULL,         -- jieba 分词后空格连接，供 FTS
  embedding BLOB,                       -- 可空，阶段五启用
  UNIQUE(doc_id, idx)
);

CREATE VIRTUAL TABLE chunks_fts USING fts5(
  tokenized_text, content='chunks', content_rowid='id',
  tokenize='unicode61'                  -- 分词已在应用层完成
);

CREATE TABLE tags (id INTEGER PRIMARY KEY, name TEXT UNIQUE, color TEXT);
CREATE TABLE document_tags (doc_id TEXT, tag_id INTEGER, PRIMARY KEY(doc_id, tag_id));
CREATE TABLE links (
  from_doc TEXT, to_doc TEXT, kind TEXT,  -- wiki | reference | similar(算法建议)
  PRIMARY KEY(from_doc, to_doc, kind)
);
CREATE TABLE conversations (id TEXT PRIMARY KEY, title TEXT, created_at TEXT, updated_at TEXT);
CREATE TABLE messages (
  id INTEGER PRIMARY KEY, conv_id TEXT REFERENCES conversations(id) ON DELETE CASCADE,
  role TEXT, content TEXT, citations_json TEXT, created_at INTEGER
);
CREATE TABLE settings (key TEXT PRIMARY KEY, value TEXT);
```

**检索契约（前后端 API 约定，规划新增 command）**：

```ts
// search(query, filters?, page?) → 
{ hits: [{ doc_id, chunk_id, title, snippet_html,   // <mark> 高亮
           locator, score_bm25, score_vec?, matched_terms: string[],
           source_type }],
  total: number, scanned: number, took_ms: number }
```

`matched_terms` + 分数分解即"可解释"的落点（替换 D-18 的失真百分比；前端展示相对分 = score / max_score）。

**演进规则**：所有变更走 `user_version` 递增的顺序迁移脚本（`migrations/0002_xxx.sql`，规划新增目录），禁止改历史迁移；每迁移一个版本附回滚说明；JSON 序列化字段（如 `citations_json`）内部结构变更需带 `_v` 字段。现有 IPC 契约（`DocumentInfo`/`Citation`/`AnswerResult`）在阶段二保持字段兼容（只增不改不删），前端渐进迁移。

## 3.6 并发写与一致性

- **WAL + busy_timeout=5000**：读写并发（问答检索 vs 后台入库）互不阻塞；
- **单一写入口**：所有写操作经同一 `Storage` 结构体（内部 `Mutex<Connection>` 写连接 + 池化只读连接），杜绝多连接写冲突；
- **入库事务边界 = 单文档**：meta + chunks + FTS 同事务提交，任何一步失败整体回滚（修复 D-15/D-16 的半截文件问题）；
- **软删除**：`deleted_at` 标记 + 30 天后清理任务；回收站恢复 = 置空标记（FTS 行随 content 表同步恢复）；
- 明确不做：多进程锁、分布式一致性——Tauri 单实例（`tauri.conf.json` 未开多窗口/多实例）前提下无此需求。

## 3.7 召回质量评测方法（阶段三的前置设施）

没有评测就没有"优化"，只有"改动"。方法：

1. **评测集**（规划新增 `eval/queries.jsonl`，随仓库版本化）：≥ 100 条查询 × 人工标注相关 chunk_id。构成：字面匹配类 40%、同义改写类 25%、跨文档综合类 15%、中英混合类 10%、无答案类（负样本，期望零命中）10%。语料用公开文档 + 自建笔记（避免真实隐私数据入仓）；
2. **指标**：Recall@5、Precision@5、MRR@10、nDCG@10；负样本单独统计误报率；
3. **执行**：Rust 侧 `cargo run --bin eval_retrieval -- --db fixture.db --queries eval/queries.jsonl`（规划新增，只读，不依赖 LLM），输出 JSON 报告；CI 在 PR 上跑并对比基线，**Recall@5 相对基线下降 > 3pp 即 fail**（防退化门禁）；
4. **对照**：现有 2-gram 算法保留为 `legacy` 策略跑同一评测集，作为基线（验证假设 A-05）；每次检索改动附评测报告，写入 06 文档 §6.5 的验收记录；
5. **端到端答案质量**（含 LLM）不进 CI（不确定性 + 费用），以 20 条固定问题的月度人工评审代替，评审表模板见 06 文档。

## 3.8 性能验收目标（拟定，环境假设见 00 文档 §0.7）

| 操作 | 现状预期 | 目标 |
| --- | --- | --- |
